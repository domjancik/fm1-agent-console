## Integration fixes made in this pass

1. **File-edit approvals (`packages/agent-adapter-traycer`).** Host 1.5.4 sends file writes as `fileEditApprovalRequested` / `fileEditApprovalResolved`, answered with `fileEditApprovalDecision`, with pending items in `snapshot.pendingFileEditApprovals`. The chat channel ignored these. Worse, when it reconciled its pending set it **auto-resolved the matching approval that the notification feed had just reported**, 4 ms later. The first live T7 run shows this, and it ended BLOCKED (`reports/evidence/e2e/t7-diagnosis/`). The channel now tracks both kinds, and decisions use the matching frame. Two fake-host tests were added.
2. **Feeds after a late first connect (adapter).** If the host was down when `connect()` ran, the background reconnect later connected, but the three event feeds were never started, so the console never got live state. The adapter now starts them on that first successful connect. The extended test fails without the fix.
3. **First activity frame (adapter).** `listSessions()` now waits up to 2 s for the first `agent.activity.subscribe` frame. Without this wait, a console that resyncs right after connecting lists every chat as `unknown`, which agent-core refuses to prompt. This is the `observed=null` refusal the companion reported. A new option, `firstActivityWaitMs`, controls it; two tests were added.
4. **Selected-session watch (`apps/companion/src/session-watch.ts`).** The companion now calls the adapter's `watchSession()` for the device's live selection, which opens `chat.subscribe` for that chat only, and releases the previous watch.
5. **`--emu` device mode** for the companion, and `test traycer … -- <runner args>` passthrough.
6. `apps/companion/test/traycer-integration.test.ts` runs the real `TraycerAgentAdapter` against the fake host, behind the Companion, driven over the device link. It is typechecked by `tsconfig.traycer.json`, because the vendored protocol does not build under `noUncheckedIndexedAccess`.
